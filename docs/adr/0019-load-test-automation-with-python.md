# 부하 테스트 자동화와 그래프는 Python으로 하고, 스크립트는 `perf/`, 결과는 `docs/performance/`에 둔다

부하 테스트 한 번은 DB 초기화 → 워밍업 → k6 실행 → 앱·DB 지표 수집 → 정합성 검사 → 집계로 이어진다. 단계별 VU와 N_max 탐색까지 사람이 손으로 돌리면 실행마다 조건이 달라진다. 그래서 이 흐름을 스크립트 하나로 묶는다.

- **오케스트레이션·집계·그래프**: Python 3 + pandas + matplotlib. 실행 순서 제어, `docker exec`로 MySQL 지표 수집, Actuator 폴링, k6 CSV 집계, PNG 생성을 같은 언어로 처리한다.
- **부하 발생**: k6(ADR 0016).
- **위치**: k6 스크립트·시드·오케스트레이터는 `perf/`에 둔다. 집계 CSV·PNG·보고서는 `docs/performance/`에 둔다. 요청 단위 원본(k6 CSV)은 수십 MB라서 `perf/out/`에 두고 커밋하지 않는다.
- **시나리오 두 개**
  - **오픈 피크**: ADR 0017 그대로. 활성 회원 N명이 동시에 출발하는 방식이고, N_max와 입장 인원을 판정한다.
  - **정상 부하**: VU 10/25/50/100/150을 단계마다 3분씩 유지한다. 좌석 조회 3회(4~6초 간격) 뒤에 선점하고 떠난다. 처리량·자원 추이와 병목 징후를 관찰하는 데 쓴다. 조회 p95 300ms, 오류율 0.1%는 이 시나리오의 참고선이고, 판정 기준은 ADR 0017을 유지한다.

**선택 이유 (사용자)**: 대화에서 AI 추천에 동의했다. 직접 쓴 이유로 바꿀 것.

## Considered Options

- **Grafana + Prometheus**: 실시간 대시보드는 좋지만 컨테이너가 늘고, 포트폴리오용 PNG를 내보내는 과정이 번거롭다.
- **PowerShell 스크립트**: 실행은 되지만 CSV 집계와 그래프를 따로 다른 도구로 만들어야 한다.

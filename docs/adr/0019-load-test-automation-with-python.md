# 부하 테스트 자동화와 그래프는 Python으로 하고, 스크립트는 `perf/`, 결과는 `docs/performance/`에 둔다

부하 테스트 한 번은 DB 초기화 → 워밍업 → k6 실행 → 앱·DB 지표 수집 → 정합성 검사 → 집계로 이어진다. 단계별 VU와 N_max 탐색까지 사람이 손으로 돌리면 실행마다 조건이 달라진다. 그래서 이 흐름을 스크립트 하나로 묶는다.

- **오케스트레이션·집계·그래프**: Python 3 + pandas + matplotlib. 실행 순서 제어, `docker exec`로 MySQL 지표 수집, Actuator 폴링, k6 CSV 집계, PNG 생성을 같은 언어로 처리한다.
- **부하 발생**: k6(ADR 0016).
- **측정 대상**: `run.py --target local|aws`. 측정 순서·판정·결과 형식은 같고, 초기화·SQL 실행·앱 재시작·자원 수집만 `perf/target.py`에서 대상별로 다르다. AWS는 SSH 터널로 RDS에 붙고(pymysql), CloudWatch에서 CPU 크레딧을 가져온다(boto3). 접속 정보는 커밋하지 않는 `.env.aws`에 둔다(`perf/aws.env.example`).
- **위치**: k6 스크립트·시드·오케스트레이터는 `perf/`에 둔다. 집계 CSV·PNG·보고서는 `docs/performance/`에 둔다. 요청 단위 원본(k6 CSV)은 수십 MB라서 `perf/out/`에 두고 커밋하지 않는다.
- **시나리오**
  - **오픈 피크**: ADR 0017 그대로. 활성 회원 N명이 동시에 출발하는 방식이다. 두 가지로 돌린다.
    - **단계 측정**(`run.py ladder`): 좌석 수마다 10 → 20 → 40 → … → 좌석 수/2명을 한 번씩 잰다. 개선 전후 비교와 병목 탐색에 쓴다.
    - **N_max 탐색**(`run.py peak`): 좌석 수마다 N_max와 입장 인원을 판정한다.
  - 조회 경로의 비용을 쪼개 보는 조회 단독 실험은 미리 만들지 않는다. 오픈 피크 결과에서 조회가 다시 병목으로 판단될 때 추가한다.
  - 정상 부하(VU를 단계마다 몇 분씩 유지)는 재지 않는다. 대상이 최대 1,000석이 되면서(ADR 0021) 측정 도중에 매진되어 결과가 왜곡된다. 선착순 서비스의 품질은 오픈 피크가 정한다.

## Considered Options

- **Grafana + Prometheus**: 실시간 대시보드는 좋지만 컨테이너가 늘고, 포트폴리오용 PNG를 내보내는 과정이 번거롭다.
- **PowerShell 스크립트**: 실행은 되지만 CSV 집계와 그래프를 따로 다른 도구로 만들어야 한다.

# 성능 품질 기준과 입장 인원 산정

서버와 DB는 각각 2 vCPU·1 GiB이고 확장하지 않는다. 그래서 처리량을 높이는 대신, 품질 기준을 지키는 최대 **활성 회원** 수(N_max)를 실측하고 그만큼만 입장시킨다. 판정 기준은 사용자 품질 두 가지뿐이고, 자원 사용률은 병목을 찾는 데만 쓴다.

## 기준

- **응답 시간**: 예매 오픈 피크에서 좌석 조회·선점 p95 500ms 이하. 회원이 결과를 1초 안에 보고 그중 서버 몫을 절반으로 잡은 **제품 결정**이며, 인프라 사양이나 다른 서비스 수치에서 역산한 값이 아니다. 선점 p95에는 201과 정상 충돌(`SEAT_ALREADY_HELD` 409)을 모두 넣는다. 평상시/피크를 나누지 않는다. 선착순 서비스는 피크가 전부다. p95는 **k6 p95**로 판정한다. k6는 앱과 같은 서브넷에서 돌려(ADR 0016) 회원이 겪는 시간에 가깝게 잰다. 서버 쪽 처리 시간(`perf` 프로파일의 Tomcat 접근 로그 `%{us}T`)은 함께 기록해 지연이 서버 안 어디서 생기는지 가르는 데 쓴다. AWS에서 둘의 차이는 컸다. 750석 80명 조회가 서버 143ms, k6 613ms였고, 대부분 Tomcat이 처리를 시작하기 전에 기다린 시간이었다. 2026-11-01 AWS 250석 측정만 PC의 k6를 써서 서버 쪽 p95로 판정했다(집 회선이 결과를 흐렸기 때문).
- **오류**: 실행마다 시스템 오류 0건. 5xx, 2초(SLO의 4배)를 넘는 클라이언트 타임아웃, 시나리오가 예상하지 않은 4xx를 센다. 비율 목표(예: 0.1%)는 검증에 필요한 요청 수 계산이 따라와 쓰지 않는다.
- **자원**: CPU·CPU 크레딧·메모리 사용률 목표는 두지 않는다. 확장하지 않으니 사용률 목표가 결정을 바꾸지 않는다. OOM·재시작은 오류로 본다.

## 측정 방법

- **활성 회원 1명의 행동**: 실제 회원이 좌석 선택 화면에서 하는 행동을 따른다.
  1. 모든 회원이 동시에 출발한다(=예매 오픈). 들어오자마자 구역 목록을 받아 구역 하나를 균등하게 무작위로 고르고, 그 구역의 좌석을 조회한다(ADR 0023). 구역을 고르는 시간은 넣지 않아 조회가 같은 순간에 몰리는 가장 불리한 조건으로 잰다.
  2. 0.5~1초 동안 고른 뒤, 같은 열에 붙어 있는 빈 좌석 2석을 무작위로 골라 선점한다. 일행과 붙어 앉으려는 회원을 흉내 낸 것이다. 앞쪽·가운데 같은 좌석 선호는 넣지 않는다.
  3. 409(`SEAT_ALREADY_HELD`)면 같은 구역의 좌석을 다시 조회하고, 다시 0.5~1초 고른 뒤 다른 붙은 2석을 선점한다. 프론트가 409를 받으면 좌석을 다시 불러오는 것과 같은 흐름이다. 3회 실패하거나 붙은 빈 좌석이 없으면 떠난다.
  4. 선점에 성공하면 끝난다. 결제는 넣지 않는다. 결제를 붙여도 최대 활성 선점 수는 그대로 측정되기 때문이다.
- **좌석 수**: 회차 좌석 수를 250 → 500 → 750 → 1,000석으로 늘려 가며 단계마다 N_max를 잰다(ADR 0021). 실제로는 250·500·750석을 쟀고, 1,000석은 남은 병목이 좌석 수에 비례한다는 것을 확인한 뒤 재지 않았다.
- **매진을 섞지 않는다**: N_max 탐색에서는 활성 회원 × 2석 ≤ 좌석 수로 둔다. 매진이 섞이면 실패가 서버 한계 때문인지 좌석이 바닥나서인지 구분할 수 없다. 매진 상황은 별도 시나리오로 재며, 그 모양은 좌석 수별 N_max를 본 뒤 정한다.
- **N_max 탐색**: 10 → 20 → 40 → 80명으로 두 배씩 늘려 처음 실패하는 구간을 찾고, 마지막 통과와 첫 실패 사이를 이분 탐색해 **2명 간격**까지 좁힌다. 탐색 상한은 좌석 수의 절반이다. 상한에서도 통과하면 그 좌석 수에서는 매진에 필요한 회원을 모두 들여보내도 된다고 판단한다(입장 인원 = 좌석 수/2). 실행 한 번이 예매 오픈 한 번이다.
- **반복과 초기화**: 최종 N_max 지점에서 3회 반복한다. 매 실행 전 DB를 새로 만들고 같은 시드 데이터를 넣는다.
- **기준선은 단계 측정으로 잰다**: 개선 전 기준선은 N_max 탐색 없이, 좌석 수마다 10 → 20 → 40 → … → 좌석 수/2명을 한 번씩 잰다(단계 측정). 중간에 실패해도 다음 단계로 간다. 회원 수에 따라 지표가 어떻게 변하는지와 병목을 보는 것이 목적이다. N_max 탐색은 프로젝션과 1초 캐시를 모두 넣은 뒤에 한다.

## 입장 인원

```
편차    = (3회 중 최댓값 − 최솟값) / 최솟값
입장 인원 = 3회 중 최솟값 × (1 − 편차)
```

예: 190·200·210명 → 편차 ≈ 10.5% → 입장 인원 ≈ 170명. 여유 비율을 가정(예: "트래픽 30% 증가")으로 정하지 않고 측정 편차에서 얻는다.

## Considered Options

- **평상시 p95 500ms / 피크 1초 두 단계**: 피크에 1초를 허용하면 대기열이 필요한지 판단할 기준선이 흐려진다.
- **응답 시간 예산 배분(서버 500 + 네트워크 200 + 프론트 200 + 여유 100)**: 네트워크 200ms는 근거가 없는 숫자다(서울 리전 왕복은 수십 ms).
- **CPU 65% 상시 / 24시간 평균 10%**: 앞쪽은 T 계열 크레딧 모델과 맞지 않는다. 뒤쪽은 AWS가 정한 값이라 근거는 있지만, 확장하지 않는 구조에서는 결정을 바꾸지 않는다.
- **입장 여유 25%("순간 30% 증가" 가정)**: 대기열이 입장 인원을 막고 있으면 회원 수가 30% 늘 일이 없다. 그래서 가정이 순환한다. 요청이 몰리는 효과는 동시 출발 시나리오에 직접 넣었다.

# 회원은 대기열 서버를 거쳐 입장하고, 입장 인원과 초당 입장 수를 함께 제한한다

AWS 측정(ADR 0023)에서 750석 3구역의 입장 인원은 122명이었고, 160명을 넘기면 선점의 순간 몰림이 다음 병목이었다. 모든 회원이 같은 순간 출발해 0.5초 안에 선점 수백 건이 커넥션 10개 앞에 줄을 섰다. 처리량이 모자란 것이 아니라 도착이 한순간에 몰린 것이다. 그래서 회원은 대기열에 줄을 서고, 차례가 되면 입장권을 받아 예매 서버에 들어간다. 대기열은 안에 있는 회원 수와 들어오는 속도를 함께 제한한다.

## 입장 방식

매초 아래 인원만큼 줄 앞에서부터 들여보낸다.

```
이번 1초에 입장 = min(R, N − 활성 회원 수, 줄 길이)
```

- **N(입장 인원)**: 품질 기준(ADR 0017)을 지키며 예매 서버가 동시에 받을 수 있는 활성 회원 수. 측정으로 정하며, 지금은 122명이다.
- **R(초당 입장 수)**: 한 번에 몰리지 않도록 1초에 들여보내는 최대 인원. 대기열 측정으로 정한다.
- N과 R은 **대기열 서버의 설정값**이다. 회차의 값이 아니라 예매 서버의 수용량이기 때문이다. 활성 회원은 **모든 회차를 합쳐** 센다. 회차마다 N을 두면 두 회차가 같은 시각에 오픈할 때 예매 서버에 2N명이 들어온다.
- 측정한 값을 그대로 설정에 넣는다. 구역당 좌석 수 같은 값으로 N을 계산하지 않는다. 측정점이 하나뿐이라 공식을 세우면 외삽이 된다.
- 활성 회원의 자리는 선점에 성공했을 때, 그리고 입장권이 만료됐을 때 빈다.

## 구성

```
회원 ─▶ 대기열 서버 (별도 EC2, queue 모듈)
          줄 서기 · 순번 · 입장권 발급, 상태는 메모리
                │ 회차 정보 조회 GET /api/showtimes/{id} (캐시)
                ▼
회원 ─(입장권)─▶ 예매 서버: 구역 목록 · 구역 좌석 · 선점
                └─ 선점 성공 → 대기열 서버 내부 API로 자리 비움 알림
```

- **대기열 서버**: 같은 저장소의 별도 Gradle 모듈 `queue`. 독립된 Spring Boot 앱으로, 예매 서버와 다른 EC2에서 돈다. 루트의 예매 앱은 그대로 둔다. 대기자의 순번 조회가 예매 서버의 CPU를 쓰지 않게 하려고 서버를 나눈다.
- **상태**: 줄과 활성 회원은 대기열 서버의 메모리에 둔다. Redis는 쓰지 않는다. 대기열 서버가 한 대라 상태를 공유할 곳이 없다. 대기열 서버가 재시작하면 줄이 사라지며, 측정용 배포라 받아들인다.
- **줄**: 회차와 상관없이 **하나**다. 도착 순서대로 번호표를 준다. 회차를 등록할 때 오픈 시각이 겹치지 않게 할 계획이라, 보통은 한 회차의 회원만 줄에 있다.
- **회차 정보**: 대기열 서버는 회차가 있는지와 예매 오픈 시각만 알면 된다. 예매 서버의 공개 API `GET /api/showtimes/{showtimeId}`(새로 만든다)로 받아 회차별로 캐시한다.

## queue 모듈 구조

```
queue/
├── build.gradle      webmvc, security, oauth2-resource-server, actuator. JPA·DB 없음
└── src/main/java/com/ticketflow/queue/
    ├── QueueApplication
    ├── domain/queue/
    │   ├── controller/   줄 서기·순번·대기 취소, 자리 비움 내부 API
    │   ├── service/      줄과 입장 처리, 입장권 발급
    │   └── client/       예매 서버의 회차 조회 (ADR 0015)
    └── global/
        ├── config/
        └── exception/
```

- 루트 프로젝트(예매 서버)는 그대로 두고 `settings.gradle`에 `queue`만 더한다. 플러그인 버전은 루트를 따른다. 포트는 8081이다.
- 패키지는 예매 서버와 같은 모양(ADR 0001)으로 둔다. 저장소가 없으므로 `repository`는 없고, `entity`는 JPA 엔티티 자리라 두지 않는다. 줄의 상태와 규칙을 담는 클래스는 `service`에 두고 시계를 주입받는 순수 Java로 만든다.
- 응답 형식(`ProblemDetail` + `code`)과 회원 JWT 검증 설정은 예매 서버에서 **복사**한다. 공통 모듈은 두지 않는다. 두 서버는 HTTP로만 이어지고 겹치는 코드는 200줄 안팎이다. 응답 형식이 바뀌면 두 곳을 고친다.
- 브라우저는 대기열 서버를 **직접** 부른다. 프론트는 빌드 설정 `VITE_QUEUE_URL`로 주소를 받고, 대기열 서버는 CORS로 예매 서버의 출처만 허용한다. 로컬에서는 Vite 프록시가 `/api/showtimes/*/queue`만 8081로 보낸다. 예매 서버가 대신 전달하면 순번 폴링이 예매 서버를 지나가 서버를 나눈 이유가 사라진다.

## 입장권

- 대기열 서버가 **입장권 전용 키**로 서명한 JWT(HS256). 회원 JWT와 키를 나눠, 한쪽 키가 새도 다른 쪽 토큰을 만들 수 없게 한다.
- 담는 것: 회원 id(`sub`), 회차 id, 만료 시각, 입장권 id(`jti`).
  - 회원 id: 예매 서버가 회원 JWT의 회원과 같은지 확인한다. 받은 입장권을 다른 회원이 쓸 수 없다.
  - 회차 id: 다른 회차에는 쓸 수 없다.
  - 입장권 id: 다 쓴 입장권을 막는 데 쓴다.
- **유효 시간 5분**, 입장 순간부터 센다. 선점 유효 시간(5분)과 같다. 늦게 받으러 온 회원은 남은 시간만큼만 쓴다.
- 요청 헤더 `X-Entry-Token`으로 보낸다. `Authorization`에는 회원 JWT가 그대로 간다.
- 예매 서버는 대기열 서버에 묻지 않고 서명과 만료만으로 검증한다.

| API | 입장권 |
|---|---|
| 공연 목록, 공연의 회차 목록, 회차 조회 | 필요 없음 |
| 구역 목록, 구역 좌석 조회, 선점 | **필요** |
| 결제, 선점 취소 | 필요 없음 (선점을 가진 회원만 할 수 있다) |

화면 흐름: 회차 선택 → 예매하기 → 대기열(순번) → 구역 선택 → 좌석 선택 → 결제.

## 선점에 성공하면

1. 예매 서버가 대기열 서버의 내부 API를 불러 자리 하나가 비었다고 알린다. 내부 API는 서버끼리 공유하는 비밀값 헤더로 보호하고, 대기열 서버의 보안 그룹은 예매 EC2와 개발자 IP에만 연다. 알림이 실패하면 입장권 만료로 자리를 돌려받는다.
2. 예매 서버가 그 입장권 id를 **다 쓴 입장권 목록**에 넣는다. 이 목록은 Caffeine에 두고 5분 뒤 지운다. 목록에 있는 입장권은 남은 시간이 있어도 거부한다. 좌석을 더 사거나 다시 고르려면 다시 줄을 선다.

## 순번 확인

- 화면이 주기적으로 묻는다(폴링). 다음에 물을 때까지의 간격은 서버가 응답에 담는다. 앞에 R × 3명 이하가 남았으면 1초, 그 밖에는 3초다.
- 순번 = 내 번호표 − 들여보낸 마지막 번호. 줄을 세지 않고 바로 계산한다. 앞에서 떠난 회원만큼 실제보다 크게 보일 수 있지만, 실제보다 작게 보이지는 않는다.
- 차례가 되면 폴링 응답에 입장권을 담아 준다.

```
POST   /api/showtimes/{showtimeId}/queue      줄 서기
GET    /api/showtimes/{showtimeId}/queue/me   순번, 다음 확인까지 초 / 차례가 되면 입장권
DELETE /api/showtimes/{showtimeId}/queue/me   대기 취소
```

- 줄 서기와 순번 확인에는 로그인이 필요하다. 대기열 서버도 회원 JWT 서명 키(`JWT_SECRET`)로 회원을 확인한다.
- 줄 서기는 예매 오픈 시각부터 받는다. 오픈 전에 "예매하기"는 막는다.

## 중복과 이탈

| 상황 | 동작 |
|---|---|
| 기다리는 중에 새로고침, 다른 탭, 다른 기기, 줄 서기 재요청 | 같은 번호표를 돌려준다 |
| 입장한 뒤 새로고침 | 같은 입장권(같은 입장권 id와 만료 시각)을 돌려준다 |
| 입장권을 다 썼거나 만료된 뒤 다시 줄 서기 | 맨 뒤에 새 번호표를 준다 |
| 마지막 순번 확인 뒤 2분이 지남 | 줄에서 뺀다. 숨긴 탭의 타이머를 브라우저가 1분 간격까지 늦출 수 있어 그보다 길게 잡는다 |
| 대기 취소(화면의 "취소" 버튼) | 줄에서 바로 뺀다 |

## Considered Options

- **빈자리만큼만 입장(속도 제한 없음)**: 오픈 순간 N명이 한꺼번에 들어와 지금과 같은 순간 몰림이 생긴다.
- **일정 간격 묶음 입장**: 묶음 크기와 간격을 정해야 하고, 안의 인원이 빠지는 속도와 맞지 않으면 N을 넘기거나 자리를 비운다.
- **같은 앱에 프로파일로 대기열 기능 넣기**: 이미지가 하나라 배포가 쉽다. 하지만 두 서버의 코드가 한 코드베이스에 섞이고, 대기열 전용 의존성이 예매 앱에도 들어간다.
- **별도 저장소**: 경계는 가장 분명하지만 저장소, CI, 문서를 따로 만들어야 하고 이야기가 두 곳에 나뉜다.
- **Redis(대기열 EC2 안 Docker 또는 ElastiCache)**: 줄과 순번을 Sorted Set으로 다루고 재시작에도 줄이 남는다. 하지만 대기열 서버가 한 대라 공유할 상태가 없다. 학습 목적으로 넣는 것도 검토했지만, 필요해질 때 넣기로 했다.
- **서버리스(API Gateway + Lambda + DynamoDB)**: 서버 관리와 재시작 문제가 없다. 하지만 1초마다 도는 처리가 없어 입장을 계산식으로 바꿔야 하고, 새 기술이 셋이며, 콜드 스타트와 동시 실행 한도가 측정에 끼어든다.
- **예매 서버가 요청마다 대기열 서버에 입장 여부 묻기**: 입장권을 바로 취소할 수 있다. 하지만 비싼 조회 경로에 서버 간 왕복이 붙고, 대기열 서버가 멈추면 예매도 멈춘다.
- **만료로만 자리 돌려받기**: 서버 간 호출이 없다. 하지만 선점을 끝낸 회원이 5분 동안 자리를 차지해 회전이 느리다.
- **SSE·WebSocket으로 순번 밀어 주기**: 대기자 수만큼 연결을 들고 있어야 하고, 밀어 줄 정보가 순번 하나뿐이다. k6로 흉내 내기도 까다롭다.
- **회차별 N과 R(회차 컬럼)**: 회차마다 다르게 둘 수 있다. 하지만 N은 예매 서버의 수용량이라 회차의 값이 아니다.
- **오픈 전 미리 줄 서기 + 오픈 때 순서 섞기**: 네트워크 속도에 덜 좌우되어 공정하다. 하지만 상태와 처리가 하나씩 늘어난다.
- **회원 JWT를 RS256으로 바꾸고 대기열 서버에 공개 키만 주기**: 대기열 서버가 회원 토큰을 만들 수 없다. 하지만 인증 코드, 테스트, k6 서명을 모두 바꿔야 한다.

## Consequences

- 대기열 서버는 회원 JWT 키를 가지므로 회원 토큰을 만들 수 있다. 두 서버를 같은 사람이 운영해서 받아들인다. 서버가 더 늘어나면 RS256을 다시 검토한다.
- 다 쓴 입장권 목록과 대기열 상태는 각 서버 한 대의 메모리에 있다. 예매 서버나 대기열 서버를 여러 대로 늘리면 상태를 공유해야 하고, 그때 Redis를 검토한다. 같은 Redis에 분산락도 둘 수 있지만, 그러면 예매 서버가 Redis 장애를 함께 맞는다.
- 줄이 하나라 한산한 회차의 회원도 인기 회차의 줄 뒤에서 기다린다. 예매 서버를 함께 쓰므로 받아들인다.
- 측정의 활성 회원은 이제 "입장권을 받고 아직 선점에 성공하지 않았거나 입장권이 만료되지 않은 회원"이다. 대기열 측정은 대기열 없이 동시에 도착하는 경우와 대기열로 들여보내는 경우를 비교하고, 대기 시간을 함께 기록한다.

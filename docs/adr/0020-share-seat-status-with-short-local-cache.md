# 좌석 조회 응답을 1초 로컬 캐시로 공유한다

> 이 결정은 회차당 6,000석 측정에 근거했다. 대상이 최대 1,000석으로 바뀐 뒤(ADR 0021) 1,000석 이하 기준선에서도 무너지는 곳이 좌석 조회 p95와 커넥션 대기였으므로, 프로젝션에 이어 캐시를 넣고 같은 단계 측정으로 비교한다.

부하 테스트에서 가장 먼저 무너진 곳은 좌석 조회였다(`docs/performance/report.md`). DB 쿼리는 3~7ms인데, 6,000석 전체 응답(437KB)을 만들면서 엔티티·DTO·JSON을 요청마다 새로 만든다. 그 결과 Serial GC 정지와 커넥션 점유(평균 315ms)가 생겨 풀이 고갈됐다. 같은 회차를 보는 회원은 모두 같은 응답을 받으므로, 응답을 한 번 만들어 여럿이 나눠 쓴다.

- **무엇을**: 회차별 좌석 조회 응답을 **직렬화된 JSON `byte[]`**로 캐시한다. 캐시가 맞으면 Jackson 직렬화도 건너뛴다. 클라이언트가 받는 JSON은 바뀌지 않는다.
- **어디에**: 앱 프로세스 안의 로컬 캐시(Caffeine). 서버는 한 대이고 확장하지 않는다(ADR 0016).
- **얼마나**: 쓰고 나서 1초 뒤 만료(`expireAfterWrite`). 선점·취소·결제 때 캐시를 비우지 않는다. 피크에는 선점이 계속 일어나서, 비우는 방식으로는 캐시가 거의 항상 비어 있게 된다.
- **만료 순간 몰림**: 같은 회차에 동시에 미스가 나면 한 요청만 계산하고 나머지는 그 결과를 기다린다(`Cache.get(key, loader)`).
- **정합성**: 캐시는 보여 주기만 한다. 선점·결제·취소는 지금처럼 `SeatOccupancyLock`이 DB 락으로 검증한다. 화면이 최대 1초 낡은 대가는 409 `SEAT_ALREADY_HELD`가 조금 느는 것이다.
- **내 선점 표시**: 방금 선점한 회원에게 자기 좌석이 최대 1초 동안 빈 좌석으로 보일 수 있다. 프론트가 선점 응답의 좌석을 "내 선점"으로 덮어 표시한다. 새로고침해도 유지되도록 선점을 회원·회차별로 `sessionStorage`에 저장하고, 만료 전이면 복원한다. 다른 탭·기기까지 복원하는 "내 선점 조회" API는 두지 않는다.
- **시간**: 운영은 Caffeine 기본 `Ticker`(단조 증가 시계)를 쓴다. 테스트는 `Ticker` 빈을 가짜로 바꿔 끼워 1초를 기다리지 않고 흘린다. 테스트마다 시작 전에 캐시를 비운다.

**선택 이유 (사용자)**: 지금 문제는 조회다. 실제 공연 예매 화면도 좌석 상태가 실시간으로 반영되지 않고, 좌석을 고른 뒤에야 누군가 먼저 선점했다고 알려 주는 방식이다. 그래서 1초 늦은 상태를 보여 주는 것은 받아들일 수 있다.

## Considered Options

- **DTO 목록(`List<SeatResponse>`) 캐시**: 컨트롤러 반환 타입이 그대로라 읽기 쉽다. 하지만 437KB 직렬화가 요청마다 남아서 GC 압박이 이어진다.
- **선점·취소·결제 성공 시 캐시 삭제**: 바뀐 직후부터 반영되지만, 피크에는 캐시가 거의 맞지 않는다.
- **Redis 캐시**: 서버가 한 대라 공유할 필요가 없다. 오히려 요청마다 437KB를 네트워크로 받아 와야 한다.
- **배치도/상태 API 분리**: 응답이 작아지지만 API 모양과 프론트가 바뀐다. 캐시 효과를 측정한 뒤 판단한다.
- **Spring `ConcurrentMapCache`**: 만료(TTL)가 없다. 직접 만든 캐시는 만료 순간 몰림을 막는 코드를 손으로 짜야 해서 위험하다.

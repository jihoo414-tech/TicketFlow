# 여러 테스트가 함께 쓰는 준비 데이터는 테스트 쪽 `fixture` 패키지에 둔다

여러 테스트 클래스가 같은 준비(given) 데이터를 쓰게 되면, 그 데이터를 만드는 코드를 `src/test/java/com/ticketflow/fixture/`에 둔다. 이 패키지는 테스트 소스에만 있고, 앱 코드의 구조(ADR 0001)에는 영향을 주지 않는다. 데이터를 담는 record(예: `HoldFixture`)와, 리포지토리로 그 데이터를 저장하는 `@Component` 팩토리(예: `HoldFixtureFactory`)로 나눈다.

팩토리는 `@Import`가 아니라 `@Component`로 둔다. 그러면 컴포넌트 스캔으로 등록되고, 모든 기능 테스트가 같은 컨텍스트 설정을 그대로 공유한다(ADR 0005).

**선택 이유 (사용자)**: 좌석·회차·회원 준비 코드가 선점 테스트마다 반복되고, 동시성 테스트도 같은 데이터를 쓴다. 직접 쓴 이유로 바꿀 것.

## Considered Options

- **테스트 클래스 안의 private 메서드**: 가장 단순하다. 하지만 동시성 테스트처럼 다른 클래스에서 같은 데이터를 만들면 코드를 복사하게 된다.
- **같은 패키지(`domain/booking`)에 파일만 분리**: 새 패키지가 필요 없다. 하지만 다른 도메인의 테스트가 이 fixture를 쓰면 위치가 어색해진다.
- **`@TestComponent` + `@Import`**: 테스트 전용 빈임이 명확하다. 하지만 `@Import`하는 클래스마다 컨텍스트 설정이 달라져서 컨텍스트가 여러 번 뜬다.

## Consequences

- fixture가 정한 값(예: 예매 오픈 시각 `BOOKING_OPEN_AT`)을 테스트가 공유한다. 이 값을 바꾸면 그 값으로 단언하는 테스트가 함께 바뀐다.
- `@Component`라서 테스트 컨텍스트에는 항상 팩토리 빈이 등록된다. 앱 실행에는 들어가지 않는다.
- ADR 0005의 원칙은 그대로다. fixture는 API가 없는 데이터(공연·회차·좌석·회원)만 리포지토리로 만든다. 선점·예매는 API로 만든다.

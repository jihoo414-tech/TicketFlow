# 부하 테스트는 자원을 제한한 로컬 컨테이너와 k6로 하고, AWS에서 최종 검증한다

배포 대상은 EC2 t3.micro(2 vCPU, 1 GiB)와 RDS db.t4g.micro(2 vCPU, 1 GiB)이고, 스케일업·스케일아웃은 하지 않는다. 테스트 코드·데이터·병목 개선은 로컬에서 반복하고, 절대 용량은 AWS에서 한 번 확정한다.

로컬은 `docker-compose.aws.yml`로 앱과 MySQL을 각각 컨테이너로 띄우고 CPU·메모리를 제한한다. 앱 컨테이너는 EC2의 1 GiB에서 OS 몫을 뺀 850 MiB로 두고, EC2에 쓸 JVM 옵션을 그대로 넣는다. MySQL은 RDS 기본 파라미터 그룹을 흉내 내 버퍼 풀을 메모리의 3/4로 두며, AWS에서 실제 값을 확인해 교정한다. 부하는 k6로 발생시킨다.

로컬 결과는 개선 전후 비교와 병목 탐색에만 쓴다. CPU 종류, EC2↔RDS 네트워크 지연, 스토리지 IOPS, CPU 크레딧은 로컬에서 재현하지 않는다(크레딧 소진 시나리오는 복잡도 대비 이득이 작아 제외).

**AWS 측정 방식(2026-11-01 추가)**
- 앱은 EC2에서 로컬과 같은 Docker 이미지와 JVM 옵션으로 실행한다. 리전은 서울, CPU 크레딧 모드는 **Unlimited**다(크레딧이 바닥나도 CPU를 10%로 묶지 않고, 초과분은 과금된다).
- 부하 발생기(k6)는 **앱과 같은 서브넷의 EC2(t3.small)**에서 돌린다. 처음엔 비용을 줄이려고 개발자 PC에서 돌렸으나, 500석 250명에서 집 회선이 수백 명분의 좌석 응답을 받느라 k6 타임아웃 11건이 났다(같은 실행의 서버 p99는 55ms). 부하 발생기가 먼저 한계에 닿으면 서버 한계가 아니라 측정 도구의 한계를 재게 된다. `run.py`는 `AWS_K6_HOST`가 있으면 스크립트를 그 EC2로 올려 ssh로 실행하고 결과를 받아 온다. 250석 결과(2026-11-01)만 PC의 k6로 쟀다.
- 앱 포트는 개발자 IP에만 연다. RDS는 외부에 열지 않고 EC2를 거친 SSH 터널로 초기화·지표 수집을 한다.
- 로컬에서는 N_max 탐색을 하지 않고 AWS에서 바로 한다. 로컬 결과는 개선 전후 비교로 충분히 썼고, 남은 흔들림(COMMIT 지연, 같은 PC의 k6)은 로컬 환경 탓이다.
- 이 배포는 부하 측정용이다. 회원 인증(ADR 0022)을 넣은 뒤에도 HTTPS를 두기 전까지는 외부에 공개하지 않는다.

## Considered Options

- **처음부터 AWS에서 테스트**: 실제 수치를 얻지만 반복할 때마다 크레딧과 비용을 쓰고, 개선 전후 비교를 빠르게 돌릴 수 없다.
- **앱은 IDE에서, DB만 컨테이너로**: 앱에 자원 제한이 걸리지 않아 1 GiB 메모리 압박을 관찰할 수 없다.
- **PC의 k6 + 서버 쪽 p95로만 판정**: k6 EC2 비용이 없다. 하지만 오류(타임아웃)까지 집 회선에 좌우되고, 회원이 겪는 시간을 잴 수 없다.

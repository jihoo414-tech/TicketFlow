# 부하 테스트는 자원을 제한한 로컬 컨테이너와 k6로 하고, AWS에서 최종 검증한다

배포 대상은 EC2 t3.micro(2 vCPU, 1 GiB)와 RDS db.t4g.micro(2 vCPU, 1 GiB)이고, 스케일업·스케일아웃은 하지 않는다. 테스트 코드·데이터·병목 개선은 로컬에서 반복하고, 절대 용량은 AWS에서 한 번 확정한다.

로컬은 `docker-compose.aws.yml`로 앱과 MySQL을 각각 컨테이너로 띄우고 CPU·메모리를 제한한다. 앱 컨테이너는 EC2의 1 GiB에서 OS 몫을 뺀 850 MiB로 두고, EC2에 쓸 JVM 옵션을 그대로 넣는다. MySQL은 RDS 기본 파라미터 그룹을 흉내 내 버퍼 풀을 메모리의 3/4로 두며, AWS에서 실제 값을 확인해 교정한다. 부하는 k6로 발생시킨다.

로컬 결과는 개선 전후 비교와 병목 탐색에만 쓴다. CPU 종류, EC2↔RDS 네트워크 지연, 스토리지 IOPS, CPU 크레딧은 로컬에서 재현하지 않는다(크레딧 소진 시나리오는 복잡도 대비 이득이 작아 제외).

**선택 이유 (사용자)**: 대화에서 AI 추천에 동의했다. 직접 쓴 이유로 바꿀 것.

## Considered Options

- **처음부터 AWS에서 테스트**: 실제 수치를 얻지만 반복할 때마다 크레딧과 비용을 쓰고, 개선 전후 비교를 빠르게 돌릴 수 없다.
- **앱은 IDE에서, DB만 컨테이너로**: 앱에 자원 제한이 걸리지 않아 1 GiB 메모리 압박을 관찰할 수 없다.

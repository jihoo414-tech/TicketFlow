# 좌석 조회에서 점유 이력을 DB에서 필터링한다

좌석 조회는 해당 회차의 `hold_seat` 이력을 전부 가져온 뒤 Java에서 현재 점유 중인 이력만 골랐다. 이력이 쌓일수록 만료·취소된 이력도 조회와 객체 생성에 포함된다. 6,000석 회차의 로컬 실험에서 만료 이력 1,000건과 12,000건의 조회 지연 차이를 관찰했다.

좌석 조회 쿼리의 조건에 `RESERVED` 또는 `HELD`이면서 `expires_at > now`를 적용한다. `now`는 기존과 같이 주입된 `Clock`에서 한 번 읽어 전달한다. 만료 시각 정각은 점유하지 않으며, 예약은 선점 만료 시각이 지나도 점유한다. 취소 상태는 제외한다. 점유 판단이 필요한 다른 경로는 변경하지 않는다.

## 고려한 대안

- Java에서 계속 필터링: 조건이 도메인 메서드에만 존재하지만 모든 이력을 읽는 비용이 누적된다.
- 이력 삭제: 이력 보존 및 기존 취소 처리의 전제와 충돌한다(ADR 0011, 0012).
- 인덱스 추가: DB 실행 계획과 쓰기 비용을 확인한 뒤 별도로 판단한다.

## 결과

- 조회 시 애플리케이션으로 전달되는 이력은 현재 점유 중인 이력으로 제한된다. DB가 내부적으로 읽는 행 수는 인덱스와 실행 계획에 따라 달라진다.
- 점유 조건이 도메인 메서드와 조회 쿼리에 각각 존재하므로 상태나 만료 규칙이 바뀌면 함께 변경하고 테스트해야 한다.
- 성능은 같은 데이터와 부하 조건에서 측정하며, 실제 예매·선점 생성 경로의 성능은 이 결정만으로 개선되지 않는다.

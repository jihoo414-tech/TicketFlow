# 테스트는 기능 · 동시성 · 단위 세 가지로 나누고, Mock은 쓰지 않는다

검증하려는 것이 무엇이냐에 따라 테스트 방식을 나눈다. 모든 테스트 이름은 `GLOSSARY.md`의 용어로 동작을 설명하고, 단언은 공개된 결과(HTTP 응답, 공개 메서드의 반환값)로만 한다.

| 방식 | 도구 | 검증할 것 |
|---|---|---|
| 기능 테스트 | `@SpringBootTest` + MockMvc + Testcontainers MySQL, 테스트마다 `@Transactional` 롤백 | 요청 하나의 결과. 규칙마다 대표 케이스 하나로 "그 규칙이 API까지 연결되어 있다"를 확인한다. 시간 규칙은 테스트용 시계로 시각을 정하거나 돌려서 확인한다. |
| 동시성 테스트 | 여러 스레드가 MockMvc를 동시에 호출 + Testcontainers MySQL, 롤백 없이 테스트 후 데이터 정리 | `docs/concurrency-cases.md`의 케이스. 동시 요청 뒤에도 `docs/invariants.md`가 지켜지는지 확인한다. |
| 단위 테스트 | 순수 JUnit (스프링·DB 없음) | 엔티티 메서드의 핵심 규칙. 현재 시각은 파라미터로 받는다. 경계값(정각, 1초 전후, 0·1·4·5석)을 촘촘히 확인한다. |

**준비(given) 데이터**: API가 없는 데이터(공연·회차·좌석·회원)는 리포지토리로 저장한다. API가 있는 상태(선점·예매)는 API를 호출해서 만든다. 그래야 선점·예매의 저장 구조를 바꿔도 테스트가 깨지지 않는다.

**선택 이유 (사용자)**: 실제 포트로 앱을 띄우는 방식은 느릴 것 같아 기능 테스트는 MockMvc로 한다. 동시성 테스트도 같은 도구로 한다. 단위 테스트를 엔티티 메서드로 할지 Mock 서비스로 할지는 사용자가 판단하기 어려워 AI 추천을 따랐다. 엔티티 테스트는 입력과 반환값만 보지만, Mock 테스트는 서비스가 내부에서 무엇을 호출하는지 알아야 해서 "외부에서 관찰되는 동작만 검증한다"는 원칙에 어긋나기 때문이다.

## Considered Options

- **`@WebMvcTest` + Mock 서비스**: 빠르지만, 응답 모양만 검증하고 실제 쿼리와 서비스는 검증하지 못한다. 지금은 쓰지 않고, 기능 테스트가 너무 느려지면 다시 판단한다.
- **실제 포트(`RANDOM_PORT`) + HTTP 클라이언트**: 실제 HTTP와 가장 가깝다. 하지만 테스트와 앱이 다른 스레드에서 돌아서 롤백을 쓸 수 없고 컨텍스트도 하나 더 뜬다. 실제 서버 조건은 MVP 이후 부하 테스트에서 다룬다.
- **서비스 + Mockito 단위 테스트**: 테스트가 리포지토리 호출 방식에 묶여, 규칙을 바꾸지 않은 리팩터링에도 깨진다.

## Consequences

- 단위 테스트를 하려면 규칙이 엔티티 메서드에 있어야 한다. 서비스는 조회, 저장, 순서 조립을 맡는다.
- 롤백 방식의 기능 테스트는 "커밋되어야 보이는 동작"을 검증하지 못한다. 그런 동작은 동시성 테스트가 맡는다.
- 기능 테스트들은 같은 컨텍스트 설정(테스트용 시계 포함)을 공유해서 컨텍스트가 한 번만 뜨게 한다.

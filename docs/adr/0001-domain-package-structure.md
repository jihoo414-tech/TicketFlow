# 규칙의 소유자별 패키지 + 내부 3레이어 구조로 고정

이전 두 번의 시도에서 AI가 패키지와 레이어를 계속 늘리는 바람에 구조를 따라갈 수 없게 되었다. 그래서 첫 코드를 쓰기 전에 구조를 고정한다. 패키지는 명사가 아니라 "누가 이 규칙을 소유하는가"로 나눈다.

```
com.ticketflow
├── domain/
│   ├── performance/  공연·회차·좌석 위치 (조회만)
│   ├── booking/      좌석 상태 머신 전체: 선점·선점 취소·결제→예매·선점 만료·예매 취소·내 예매 조회
│   └── member/       회원
└── global/           exception, config 두 개만
```

각 도메인 안에는 `controller` / `service` / `repository`만 둔다. 헥사고날이나 클린 아키텍처는 쓰지 않는다. 새 도메인 패키지, 새 레이어, `global/` 하위 폴더를 추가하려면 사용자 승인과 ADR이 필요하다.

**선택 이유 (사용자)**: booking 패키지가 좌석의 선점·예매·취소 흐름을 모두 관리하면 수정할 때 관리가 더 간편하다.

## Considered Options

- **`seat` / `hold` / `reservation`으로 분리** (`seat`가 상태 전이를 하고, 나머지 둘이 호출하는 방식): 폴더는 작아지지만, 4석 제한(선점 + 예매 합계)처럼 여러 모듈에 걸친 규칙의 주인이 애매해진다. 이전 시도의 실패와 같은 모양이라 채택하지 않았다.

## Consequences

- `booking`이 가장 큰 패키지가 된다. 그 안에서 파일을 어떻게 나눌지는 슬라이스마다 설계 단계에서 정한다.
- 어떤 데이터를 함께 잠그고 저장할지(애그리거트 경계)는 이 ADR의 범위가 아니다. 동시성 케이스 문서를 쓴 뒤 선점 설계 때 정한다.

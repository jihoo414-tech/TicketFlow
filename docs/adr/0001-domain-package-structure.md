# 규칙의 소유자별 패키지 + 내부 3레이어 구조로 고정

이전 두 번의 시도에서 AI가 패키지와 레이어를 계속 늘리는 바람에 구조를 따라갈 수 없게 되었다. 그래서 첫 코드를 쓰기 전에 구조를 고정한다. 패키지는 명사가 아니라 "누가 이 규칙을 소유하는가"로 나눈다.

```
com.ticketflow
├── domain/
│   ├── performance/  공연·회차·좌석 위치 (조회만)
│   ├── booking/      좌석 상태 머신 전체: 선점·선점 취소·결제→예매·선점 만료·예매 취소·내 예매 조회
│   └── member/       회원
└── global/           exception, config, init 세 개만
```

각 도메인 안에는 `controller` / `service` / `repository` / `entity`만 둔다. JPA 엔티티는 `entity`에 둔다. 헥사고날이나 클린 아키텍처는 쓰지 않는다. 새 도메인 패키지, 새 레이어, `global/` 하위 폴더를 추가하려면 사용자 승인과 ADR이 필요하다.

**선택 이유 (사용자)**: booking 패키지가 좌석의 선점·예매·취소 흐름을 모두 관리하면 수정할 때 관리가 더 간편하다.

**`entity` 패키지를 둔 이유 (사용자)**: 엔티티 파일이 도메인 바로 아래에 섞이면 경계가 흐려진다. `entity` 폴더가 있으면 폴더 이름만으로 엔티티가 어디 있는지 알 수 있고, 엔티티가 많아질 `booking`에서도 흩어지지 않고 한곳에서 볼 수 있다.

**`global/init`을 추가한 이유 (사용자)**: `data.sql`은 테스트 DB에도 들어가서 테스트가 고정된 초기 데이터와 날짜에 묶인다. 테스트와 앱의 데이터를 분리하기 위해 초기 데이터는 `local` 프로필에서만 앱 코드로 넣고, 그 코드를 `global/init`에 둔다. 테스트는 필요한 데이터를 스스로 만든다.

## Considered Options

- **`seat` / `hold` / `reservation`으로 분리** (`seat`가 상태 전이를 하고, 나머지 둘이 호출하는 방식): 폴더는 작아지지만, 4석 제한(선점 + 예매 합계)처럼 여러 모듈에 걸친 규칙의 주인이 애매해진다. 이전 시도의 실패와 같은 모양이라 채택하지 않았다.
- **엔티티를 도메인 패키지 바로 아래에 두기** (`domain/member/Member.java`): 폴더가 하나 줄지만, 엔티티와 다른 파일의 경계가 흐려져 채택하지 않았다.
- **엔티티를 `repository` 안에 두기**: 폴더 수는 그대로지만, 엔티티가 저장소의 일부처럼 읽혀 채택하지 않았다.

## Consequences

- `booking`이 가장 큰 패키지가 된다. 그 안에서 파일을 어떻게 나눌지는 슬라이스마다 설계 단계에서 정한다.
- 레이어별 폴더라서 기능 하나(예: 선점)를 고칠 때 여러 폴더를 오가야 한다. 지금 규모에서는 감수하고, 불편해지면 다시 판단한다.
- 어떤 데이터를 함께 잠그고 저장할지(애그리거트 경계)는 이 ADR의 범위가 아니다. 동시성 케이스 문서를 쓴 뒤 선점 설계 때 정한다.

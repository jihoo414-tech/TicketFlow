# 선점 요청의 조회 쿼리 개선 후보

## 배경

선점 요청은 정상 경로 기준 회원 존재 확인, 회원과 좌석 락, 회차 조회, 활성 선점 확인, 예매 좌석 수 확인, 선택 좌석 점유 확인을 위해 SELECT를 7회 수행한다. 이후 선점 1건과 선택 좌석별 이력을 저장한다.

현재 활성 선점 확인과 좌석 점유 확인은 관련 이력을 전부 조회한 뒤 Java에서 검사한다. 이력이 누적되면 불필요한 데이터 전송과 엔티티 생성 비용이 증가할 가능성이 있다. 실제 영향은 이력이 누적된 데이터로 측정해야 한다.

초기 스모크 피크 측정에서는 좌석 락 쿼리가 호출당 10,000행을 읽었지만, 후속 피크 50명 측정에서는 호출당 2행을 읽고 평균 0.388ms가 걸렸다. 두 측정의 조건은 동일하지 않으므로 시간 차이 전체를 통계 갱신의 효과로 단정하지 않는다. 성능 테스트 시드에는 `ANALYZE TABLE`이 포함되어 있다.

## 개선 후보

- [ ] 락을 획득하기 전에 좌석 ID 목록 크기(1~4개), null 및 유효성을 검증한다. 도메인 검증은 유지한다.
- [ ] 회원·회차의 활성 선점 조회를 `HELD`와 `expires_at > now` 조건을 포함한 존재 여부 조회로 변경한다.
- [ ] 선택 좌석 점유 확인을 `RESERVED` 또는 만료되지 않은 `HELD` 조건을 포함한 존재 여부 조회로 변경한다.
- [ ] `hold(member_id, showtime_id, status, expires_at)` 인덱스 후보를 기존 인덱스와 실행계획에 비추어 검토한다.
- [ ] `hold_seat(seat_id, hold_id)` 인덱스 후보를 기존 외래키 인덱스와 비교하고 쓰기 비용도 확인한다.
- [ ] 회원 존재 확인 중복을 제거할 수 있는지 다른 API의 오류 처리와 함께 검토한다.

## 유지할 동시성 규칙

회원 락을 먼저 획득하고 좌석 락을 획득하는 순서를 유지한다. 좌석 락을 획득한 후 DB에서 최신 점유 상태를 확인한다. 회원별 활성 선점 수와 좌석 수 제한, 좌석 중복 선점 방지 규칙을 유지한다.

## 검증 계획

- [ ] 활성·만료·취소·예매 상태와 만료 시각 경계에서 기존과 동일하게 판단하는지 검증한다.
- [ ] 같은 좌석 동시 선점, 같은 회원의 동시 선점, 최대 4석 제한을 통합 및 동시성 테스트로 검증한다.
- [ ] 이력이 없는 데이터와 과거 선점·취소·만료 이력이 누적된 데이터를 준비한다.
- [ ] 변경 전후 `EXPLAIN`과 읽은 행 수를 비교한다. 실제 DB의 기존 인덱스도 확인한다.
- [ ] 동일한 부하 조건에서 선점 p95, 락 대기, 커넥션 대기, DB 부하 및 인덱스 쓰기 비용을 비교한다.

이 문서 작성 시점에는 Docker 접근 권한 제한으로 현재 DB의 `EXPLAIN`을 재실행하지 못했다. 인덱스의 필요성과 개선 효과는 실측 결과로 판단한다.

# AWS 오픈 피크 측정: 좌석 수별 N_max와 구역 조회

측정일 2026-11-01 ~ 11-02. 모든 수치는 `perf/run.py`로 측정한 값이며, 추정은 그렇게 표시했다. 원본은 `docs/performance/aws/`에 있다. 로컬 단계 측정과 개선 이력은 `seat-count-report.md`에 있다.

## 요약

| 질문 | 답 |
|---|---|
| 좌석 수별 입장 인원 (구역 없음) | 250석 **전원**(125명), 500석 **57명**, 750석 **71명**. 1,000석은 재지 않았다 |
| 무엇이 먼저 무너지나 | **좌석 조회의 k6 p95.** 서버 처리 시간은 100ms 아래, 커넥션 대기는 0.1ms였다. 대부분 Tomcat이 요청 처리를 시작하기 전에 기다린 시간이다 |
| 왜 좌석이 많을수록 덜 받나 | 조회 응답이 좌석 수에 비례해 커지고(250석 약 17KB, 750석 약 50KB), 같은 순간 수십~수백 명에게 쓰는 비용이 커진다(추정) |
| 구역으로 나누면 | 750석을 3구역으로 나누자 N_max 75~92명 → **196~270명**, 입장 인원 58명 → **122명**(같은 날, 같은 코드) |
| 다음 병목 | 3구역 160명 이후 **선점의 순간 몰림**: 커넥션 10개 앞에 줄이 서며 선점 p95와 커넥션 대기가 함께 오른다 |
| 정합성·오류 | 모든 실행에서 정합성 위반 0, 서버 오류(5xx) 0 |

## 1. 환경

| 항목 | 값 |
|---|---|
| 앱 | EC2 t3.micro(2 vCPU, 1 GiB, **Unlimited** 크레딧), Docker 850 MiB, `-Xmx512m`, `perf` 프로파일 |
| DB | RDS db.t4g.micro, MySQL 8.4, `max_connections` 60, 버퍼 풀 128MB |
| 커넥션 풀 | HikariCP 10 |
| 부하 발생기 | k6, **앱과 같은 서브넷의 EC2 t3.small** (250석만 개발자 PC) |
| 판정 | k6 p95: 좌석 조회·선점 500ms 이하, 시스템 오류 0, 정합성 위반 0 (ADR 0017). 서버 p95(Tomcat 접근 로그)는 함께 기록 |
| 행동 모델 | 동시 출발 → (구역 선택) → 좌석 조회 → 0.5~1초 → 같은 열 붙은 2석 선점 → 409면 재조회, 최대 3회 |
| N_max 탐색 | 10명부터 두 배씩, 실패 구간을 2명 간격까지 이분 탐색, 상한 좌석/2, 탐색 3번. 입장 인원 = 최솟값 × (1 − 편차) |

11-02 측정은 회원 인증(JWT, ADR 0022)이 들어간 코드다. 750석 1구역 결과(75 / 92 / 88)가 인증 전 결과(75 / 73 / 73)와 흔들림 범위 안이라, 토큰 검증 비용은 측정상 드러나지 않았다.

## 2. 측정 도구를 의심한 일: 부하 발생기가 먼저 무너졌다

처음에는 비용을 줄이려고 k6를 개발자 PC에서 돌리고 서버 쪽 p95로 판정했다. 500석 250명에서 실패가 났는데, 원인이 서버가 아니었다.

| 500석 250명 (PC k6) | 값 |
|---|---|
| 시스템 오류 | 11건, 모두 k6의 2초 타임아웃(`status 0`). 서버 5xx는 0 |
| 서버 p99 조회 / 선점 | 55ms / 116ms |
| k6 p95 조회 | 1,654ms |

서버는 빨리 응답했는데, PC가 250명분의 좌석 응답을 집 회선 하나로 받다가 2초를 넘겼다. 이대로면 서버의 한계가 아니라 측정 도구의 한계를 재게 된다. 그래서 k6를 앱과 같은 서브넷의 EC2로 옮겼다(ADR 0016). 같은 조건의 250석·10명 스모크에서 k6와 서버의 차이는 수백 ms에서 수십 ms로 줄었다.

## 3. 좌석 수별 N_max (구역 없음)

원본: `peak_trials_seats{0250,0500,0750}.csv`, `peak_result_seats*.json`

| 좌석 | 탐색별 N_max | 편차 | 입장 인원 | 비고 |
|---|---|---|---|---|
| 250 | 125 / 125 / 125 | 0% | 전원(125) | PC k6, 서버 p95 판정. 상한까지 통과 |
| 500 | 103 / 80 / 101 | 28.7% | 57 | 2회차 82명에서 선점 p95가 한 번 541ms로 튐(커넥션 대기 104ms, 다른 실행은 0.1ms 안팎). 빼면 약 100 |
| 750 | 75 / 73 / 73 | 2.7% | 71 | |

실패는 500석 2회차의 한 번만 빼고 모두 **조회의 k6 p95**였다. 선점은 30ms 안팎으로 여유가 있었다.

### 3.1 조회 한 건의 시간이 어디서 쓰이나 (500석, k6 p95)

| 구간 | 103명 | 124명 |
|---|---|---|
| TCP 연결 | 69ms | 64ms |
| 요청 보내기 | 150ms | 19ms |
| 첫 바이트까지 대기 | **350ms** | **597ms** |
| 응답 받기 | 0.6ms | 1.0ms |
| 서버 처리 (Tomcat) | 6ms | 97ms |

- 응답을 받는 시간은 거의 0이다. 대역폭 문제는 아니다.
- 서버가 처리하는 시간은 짧은데, **처리가 시작되기 전**(연결 수락, 요청 읽기, 작업 스레드 배정)에서 오래 기다린다. 같은 서브넷인데 연결에 수십 ms가 걸린 것도 앱 쪽이 바빴다는 신호다.
- 커넥션 대기는 0.1ms로 DB는 한가했다.
- 같은 순간 100명 넘게 몰릴 때 vCPU 2개가 순간 포화되는 것으로 추정한다. CPU는 1초 단위로만 재서(최대 66%) 1초보다 짧은 포화는 확인하지 못했다.

### 3.2 좌석 수가 수용량을 좌우한다

| 좌석 | 조회 응답(추정) | N_max |
|---|---|---|
| 250 | 약 17KB | 125명 이상 |
| 500 | 약 33KB | 약 100명 |
| 750 | 약 50KB | 약 73명 |

서버·시나리오·선점 방식이 같고 바뀐 것은 좌석 수뿐이다. 선점은 회차 크기와 상관없이 2석만 다루므로, 좌석 수가 바꾸는 것은 **조회 응답의 크기**다. 그래서 한 번에 보여 주는 좌석을 줄이면 수용량이 오를 것이라는 가설을 세웠다.

## 4. 구역 조회 (ADR 0023)

회차의 좌석을 구역으로 나누고, 회원은 구역을 골라 그 구역 좌석만 조회한다. 가설을 검증하려고 **같은 코드, 같은 날**에 750석을 1구역(구역 없음과 같음)과 3구역(1~8번 / 9~17번 / 18~25번, 구역당 약 250석)으로 나눠 탐색했다. 회원은 구역을 균등하게 무작위로 고른다. 3구역의 탐색 3번이 **모두** 1구역 최댓값을 넘으면 효과가 있다고 미리 정했다.

원본: `peak_trials_seats0750_zones{1,3}.csv`, `peak_result_seats0750_zones{1,3}.json`

| 750석 | N_max (탐색 3번) | 편차 | 입장 인원 |
|---|---|---|---|
| 1구역 | 75 / 92 / 88 | 22.7% | 58 |
| **3구역** | **270 / 214 / 196** | 37.8% | **122** |

- 3구역 탐색 3번이 모두 1구역 최댓값(92)을 넘었다. 최솟값 기준 약 2.6배, 입장 인원 약 2.1배.
- 같은 인원에서 조회가 크게 낮아졌다.

| 인원 | 1구역 조회 / 선점 | 3구역 조회 / 선점 |
|---|---|---|
| 40 | 320 / 27ms | 135 / 37ms |
| 80 | **613** / 27ms (실패) | **220** / 34ms |
| 160 | — | 227 / 66ms |
| 270 | — | 427 / 254ms |
| 320 | — | 747 / **544ms** (실패) |

### 4.1 다음 병목: 선점의 순간 몰림

3구역은 160명을 넘기면서 선점 p95와 커넥션 대기가 함께 올랐다(160명 27ms → 270명 71ms → 320명 128ms).

- 선점 한 건은 커넥션을 15~25ms 쓴다. 커넥션 10개로 1초에 400~600건을 처리할 수 있다(추정).
- 그런데 모든 회원이 같은 순간 출발해 0.5~1초 사이에 선점하므로, 270명이면 0.5초 안에 선점 270건이 몰린다(초당 약 540건). 처리 능력과 맞먹거나 넘는 속도라 커넥션 앞에 줄이 선다.
- 같은 순간 수백 건의 조회 응답을 쓰느라 CPU가 바빠 커넥션 사용 시간도 늘고(15 → 25ms 이상), 줄이 더 빨리 쌓인다(추정).

처리량이 모자란 것이 아니라 **도착이 한순간에 몰린 것**이다. 도착을 시간에 흩는 대기열(#20)이 이 병목에 맞는 해결책이다.

### 4.2 로컬에서는 효과를 분리하지 못했다

로컬 단계 측정(`peak_ladder_seats0750_zones{1,3}.csv`)에서는 두 설정 모두 160명 통과·320명 실패로 같았다. 로컬은 k6·앱·DB가 PC 한 대를 나눠 쓰고 COMMIT이 느려 **선점 경로가 먼저** 막힌다. 조회를 줄이는 구역의 효과가 보일 수 없는 조건이었다. 병목이 다르면 같은 개선도 다르게 보인다.

## 5. 한계

- 모든 판정은 실행 한 번씩이고, 경계 근처는 같은 인원에서도 통과와 실패가 갈렸다(3구역 195~216명). 입장 인원 공식은 이 흔들림만큼 깎는다.
- 조회 비용이 응답 크기에 비례하는 CPU 비용이라는 설명은 추정이다. 0.1초 단위 CPU 기록이나 vCPU를 늘린 비교로 확인하지 않았다.
- 구역 선택은 균등 무작위다. 인기 구역에 몰리면 409와 재시도가 늘 수 있다. 입장 인원을 쏠림 조건(예: 가운데 50%)으로 검증하는 측정은 남겨 두었다.
- 1,000석과 지속 부하는 재지 않았다. 지속 부하는 대기열 측정에서 다룬다.

## 6. 재현

```bash
python perf/run.py peak --target aws --seats 750 --zones 1   # 구역 없음과 같은 대조군
python perf/run.py peak --target aws --seats 750 --zones 3   # 3구역
python perf/run.py ladder --seats 750 --zones 3              # 로컬 단계 측정
```

측정 당시 AWS 환경 설정 예시는 공개 저장소에 포함되어 있지 않다. AWS 측정에는 앱·k6 EC2 주소, RDS 접속 정보와 `AWS_JWT_SECRET` 등 별도의 환경 설정이 필요하다.

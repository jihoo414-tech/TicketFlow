# 6,000석 공연 좌석 조회 성능 실험

## 사용자 시나리오

6,000석 규모의 인기 콘서트 예매가 시작된다. 관객들은 좌석 현황을 확인한 뒤 자리를 선점한다. 원하는 좌석을 다시 고르거나 결제를 진행하지 않아 선점이 취소되거나 만료되는 일도 반복된다. 선점이 만료되면 해당 좌석은 다시 선택할 수 있지만 이력은 남는다.

시간이 흐른 뒤 새로운 관객이 좌석 화면을 열면, 서버는 이 회차의 좌석과 선점 이력을 조회해 현재 좌석 상태를 만든다. 현재 구현은 해당 회차의 만료된 이력까지 조회한 뒤 애플리케이션에서 유효한 이력을 걸러낸다. 같은 회차에 이력이 누적되면 화면 조회가 느려질 수 있다는 가설을 검증한다. 실제 문제가 발생했다고 확정한 것은 아니다.

실험 데이터는 6개 구역 A~F에 각 1,000석을 만들고, 결제 없이 만료된 선점 이력을 여러 좌석에 분산한다. 각 이력은 한 좌석을 선점한 것으로 가정한다. 1만 건과 10만 건은 가설을 관찰하기 위한 실험 규모이며 실제 트래픽 추정치는 아니다.

## 준비와 주의 사항

- MySQL 테스트 전용 DB에서 실행한다. 스크립트는 데이터 삭제 없이 전용 공연·회차·좌석과 테스트 회원·이력을 추가한다.
- DBeaver에서 백엔드가 연결된 DB를 선택한다. 별도 DB라면 백엔드도 그 DB에 연결해야 한다.
- `perf` 프로필의 `application-perf.yml`은 SQL 초기화와 Hibernate SQL 로그를 끈다. DB 스키마가 미리 준비되어 있어야 하며, 앱 시작 시 테스트 데이터가 자동으로 삭제되지 않는다. 빈 테스트 DB라면 DBeaver에서 `src/main/resources/schema.sql`을 먼저 실행한다. 이 파일은 기존 테이블을 삭제하므로 반드시 비어 있는 테스트 전용 DB에서만 실행한다.
- `local` 프로필은 SQL 로그를 다시 켤 수 있다. 아래 명령으로 `perf` 프로필을 지정해 백엔드를 실행한다. DB 접속 환경 변수는 별도로 설정해야 한다. 이미 8080 포트에 다른 백엔드가 실행 중이라면 해당 서버가 응답할 수 있으므로 먼저 구분한다.
- DBeaver에서 각 파일을 열고 **스크립트 전체 실행**으로 실행한다. 일부 문장만 실행하거나 실행 도중 실패하면 같은 연결에서 `ROLLBACK;`을 실행하고 결과를 확인한다.
- SQL을 넣는 동안에는 k6를 실행하지 않는다. 매 단계에서 동일한 회차와 k6 설정을 사용한다.

```powershell
.\gradlew.bat bootRun --args='--spring.profiles.active=perf'
```

## 1. 테스트 회차와 6,000석 생성

DBeaver에서 `01-create-showtime.sql`을 전체 실행한다. 결과의 `seat_count`가 6000인지 확인하고 `showtime_id`를 기록한다. 매번 실행하면 별도의 공연과 회차가 추가되므로 한 번만 실행한다.

기존 `seat-load-test.js`의 `showtimeId`를 방금 확인한 회차 ID로 바꾼다. 백엔드가 같은 DB를 사용한다면 브라우저 또는 PowerShell에서 다음 주소의 숫자를 바꿔 조회할 수 있다.

```powershell
Invoke-RestMethod http://localhost:8080/api/showtimes/회차ID/seats
```

## 2. 이력이 없을 때 측정

`seat-load-test.js`가 있는 `perf` 폴더에서 다음을 실행한다.

```powershell
k6 run --vus 1 --iterations 1 seat-load-test.js
k6 run --vus 5 --duration 30s seat-load-test.js
```

첫 명령은 성공 여부 확인용이다. 두 번째 결과의 `http_reqs`, `http_req_duration`의 `p(95)`, `http_req_failed`, `checks_failed`를 기록한다.

## 3. 만료된 이력 1만 건 추가

`02-add-expired-holds.sql` 맨 위에서 `@perf_showtime_id`를 1단계의 회차 ID로 바꾸고, `@perf_history_count`는 10000으로 둔다. 전체 실행한 뒤 `added_hold_seats`가 10000인지 확인한다. 선점 상태는 `HELD`지만 만료 시각이 과거이므로 현재 점유 중인 좌석으로 계산되지 않는다.

같은 k6 명령을 다시 실행하고 결과를 기록한다.

```powershell
k6 run --vus 5 --duration 30s seat-load-test.js
```

## 4. 누적 이력 10만 건으로 증가

같은 SQL 파일의 `@perf_history_count`를 `90000`으로 바꿔 전체 실행한다. 이 스크립트는 실행할 때마다 **추가**하므로, 앞 단계 1만 건과 합쳐 10만 건이 된다. 결과의 `added_hold_seats`가 90000인지 확인한다. 생성에는 시간이 걸릴 수 있다.

아래 SQL에서 `1`을 테스트 회차 ID로 바꾸고 전체 이력 수를 확인한다.

```sql
SELECT COUNT(*) AS total_hold_seats
FROM hold_seat hs
JOIN hold h ON h.id = hs.hold_id
WHERE h.showtime_id = 1;
```

동일한 k6 테스트를 다시 실행한다.

```powershell
k6 run --vus 5 --duration 30s seat-load-test.js
```

| 선점 좌석 이력 | VU | 초당 요청 수 | p95 | HTTP 실패율 | 검사 실패율 |
|---|---:|---:|---:|---:|---:|
| 0건 | 5 | | | | |
| 1만 건 | 5 | | | | |
| 10만 건 | 5 | | | | |

각 단계를 2~3회 반복하면 일시적인 PC 부하의 영향을 살펴보는 데 도움이 된다. 같은 좌석 수와 k6 설정을 유지하고 DB 쿼리 로그 수준도 동일하게 유지한다. `sleep(1)`이 있으므로 초당 요청 수는 서버 최대 처리량이 아니다. 이력 증가에 따른 변화가 보이면 DB 실행 계획과 서버 자원 사용량도 살펴본다. 로컬 측정은 실제 서비스의 수용 인원을 뜻하지 않는다.

# 좌석 점유 이력 복합 인덱스 실험

## 조건

2026-10-30 로컬 Windows에서 Spring Boot, MySQL 8.4.11, k6 2.2.0을 같은 PC에서 실행했다. 회차 1의 좌석 6,000개, 모두 만료된 HELD 이력, SQL 로그 비활성화, 조건별 5초 예열 후 30초 측정, 각 VU는 응답 후 1초 대기했다. 검사 항목은 HTTP 200이다. 각 측정은 1회씩이다.

인덱스 적용 전 수치는 `result-after-*.json`으로, DB에서 점유 이력을 필터링하도록 변경한 뒤의 이전 측정이다. 적용 후에는 같은 각 실험 DB(이력 1,000/6,000/12,000건)에 `hold(showtime_id, status, expires_at)` 인덱스를 추가해 측정했다. 12,000건은 동일 DB로 5·20·50 VU를 순서대로 실행했고, 1,000·6,000건은 각각 해당 DB에 연결하기 위해 서버를 재시작했다. 인덱스 적용 전과 후의 서버 실행 시점, JVM 상태 및 PC 자원 사용량은 통제하지 못했다.

## 실행계획과 해석

12,000건 데이터의 `EXPLAIN ANALYZE`에서 적용 전에는 `showtime_id` 인덱스로 해당 이력 12,000건을 읽은 뒤 상태·만료시간으로 필터링했다. 적용 후에는 `idx_hold_showtime_status_expires`를 사용해 `HELD`이면서 만료 전인 범위와 `RESERVED` 범위를 조회했고, 일치 행은 0건이었다. 두 경우 결과가 0건이므로 `hold_seat` 조인은 실행되지 않았다. 실행계획의 행 수는 해당 연산자가 내보낸 행 수이며, 전체 물리 디스크 읽기량을 직접 측정한 것은 아니다.

12,000건에서 평균은 낮아졌지만 20·50 VU의 p95는 높아졌다. 각 조건이 1회뿐이고 머신 부하와 캐시를 통제하지 못해 인덱스가 API 지연에 미친 효과를 확정할 수 없다. 좌석 6,000개의 조회·응답 생성과 전송 비용도 남아 있으며 원인은 추가 프로파일링이 필요하다. 1초 대기가 있는 폐쇄형 부하이므로 초당 요청은 최대 처리량이 아니다.

모든 이력이 만료된 시나리오이므로 예약과 활성 선점이 섞이거나 실제 쓰기가 발생할 때의 효과는 확인하지 못했다. 인덱스의 추가 저장 공간, 생성·상태 변경 시 쓰기 비용도 측정하지 않았다. 실제 운영 적용 전 반복 측정과 현실적인 데이터·쓰기 부하 평가가 필요하다.

새 원본 요약은 `result-index-1000-vu5.json`, `result-index-6000-vu5.json`, `result-index-12000-vu{5,20,50}.json`이다. 실험 서버는 종료했고 세 실험 DB와 추가된 인덱스는 남겨두었다.

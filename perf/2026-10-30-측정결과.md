# 좌석 조회 성능 측정 결과

## 조건

- 측정일: 2026-10-30. Windows 로컬 PC에서 백엔드, k6, Docker MySQL을 실행했다.
- 백엔드: `codex/seat-performance` 브랜치, `perf` 프로필, 포트 18080, SQL 로그 비활성화.
- DB: 별도 MySQL 8.4.11 DB `ticketflow_perf_20261030_1528`, 회차 ID 1, 좌석 6,000개.
- 데이터: 0건에서 시작해 만료된 `HELD` 좌석 이력을 1만 건, 누적 10만 건으로 추가했다. 마지막에 전체 10만 건이 만료된 상태임을 확인했다.
- k6 2.2.0, 단계별 5 VU, 30초, 각 사용자 요청 후 1초 대기. 각 측정 전 5초 예열을 했다. 단계별 본 측정은 1회다.
- HTTP 200 여부만 검사했다. 응답 내용의 정확성이나 서버 자원, DB 실행 계획은 측정하지 않았다.

| 이력 | 요청 수 | 초당 요청 수 | 평균 | p95 | 최대 | HTTP 실패율 |
|---:|---:|---:|---:|---:|---:|---:|
| 0건 | 140 | 4.51 | 105.99ms | 156.47ms | 188.57ms | 0% |
| 1만 건 | 111 | 3.69 | 353.50ms | 445.77ms | 469.25ms | 0% |
| 10만 건 | 31 | 0.94 | 4.12초 | 4.85초 | 4.94초 | 0% |

원본 요약은 `result-0.json`, `result-10000.json`, `result-100000.json`에 저장했다.

## 해석과 한계

이 환경에서는 이력이 증가하면서 좌석 조회 응답 시간이 늘었다. 10만 건의 p95는 0건의 약 31배였다. 이는 이력을 가져와 검사하는 현재 구현이 성능 저하에 기여할 수 있다는 가설과 일치한다. 다만 반복 측정과 프로파일링, DB 실행 계획 분석을 하지 않았으므로 비용의 정확한 원인과 비중을 확정할 수 없다.

응답이 느려지면 각 VU가 다음 요청을 보내기까지도 오래 걸리는 설정이다. 초당 요청 수 감소는 이런 스크립트 동작을 포함하며, 측정값을 서버의 최대 처리량이나 실서비스 수용량으로 해석할 수 없다. 단계별 샘플 수가 다르고 특히 10만 건에서는 31건이므로 p95 해석에 주의한다. 전부 만료된 선점만 생성한 단순 시나리오이므로 실제 상태 분포를 대변하지 않는다.

## 재실행

테스트 DB를 보존했다. SQL 스크립트를 다시 실행하면 데이터가 추가되므로 재실행 전 회차와 이력 건수를 확인한다. 18080 포트에서 이 브랜치의 백엔드를 테스트 DB에 연결해 실행한 뒤 PowerShell에서 다음 명령을 사용한다.

```powershell
$env:BASE_URL = 'http://localhost:18080'
$env:SHOWTIME_ID = '1'
k6 run --vus 5 --duration 30s perf/seat-load-test.js
```

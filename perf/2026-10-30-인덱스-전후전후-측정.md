# 복합 인덱스 전·후·전·후 반복 측정

## 목적과 방법

2026-10-30에 복합 인덱스 사용 여부를 번갈아 바꾸어 좌석 조회 성능을 측정했다. 로컬 Windows에서 Spring Boot, MySQL 8.4.11, k6 2.2.0을 같은 PC에서 실행했다. 회차 1의 6,000석, 만료된 `HELD` 이력 12,000건, 50 VU, 매 단계 5초 예열 후 30초 측정, 각 VU는 응답 후 1초 대기했다. 검사는 HTTP 200만 확인한다. 네 단계 모두 동일한 DB와 재시작하지 않은 같은 JVM 서버를 사용했다.

MySQL 옵티마이저가 인덱스를 선택하지 못하도록 복합 인덱스를 `INVISIBLE`로 설정해 '전'을, `VISIBLE`로 설정해 '후'를 측정했다. 숨긴 인덱스는 삭제된 것은 아니고 DB에 유지된다. 복합 인덱스가 외래 키를 지원하고 있었으므로 전·후 단계에서 동일하게 `showtime_id` 단일 인덱스를 임시로 추가했다. 각 단계 전에 별도 `EXPLAIN ANALYZE`로 예상 쿼리의 실행계획을 확인했다. 측정 후 단일 인덱스를 삭제하고 복합 인덱스를 다시 `VISIBLE`로 남겼다.

실행계획에서 전 단계는 단일 회차 인덱스로 12,000개 이력을 읽어 상태와 만료시간을 필터링했고, 후 단계는 복합 인덱스로 조건에 맞는 범위를 탐색해 0건을 반환했다. 모두 만료 상태이므로 `hold_seat` 조회는 실행되지 않았다. 실행계획은 별도로 실행한 쿼리의 결과이며 물리 디스크 읽기량이나 실제 각 HTTP 요청별 계획을 측정한 값은 아니다.

## 해석과 한계

평균과 중앙값은 두 차례 모두 인덱스 사용 시 낮았다. p95는 첫 쌍에서 560.52→320.80ms로 낮아졌지만 두 번째 쌍에서는 288.19→364.31ms로 높아져 일관되지 않았다. 따라서 이 조건에서 인덱스가 평균 응답시간을 줄였을 가능성과는 별개로, p95가 개선된다고 결론 내릴 수 없다.

각 상태가 두 번뿐이고 최초 단계의 JVM 예열이나 시간에 따른 시스템 부하 영향을 완전히 배제할 수 없다. 서버, 부하 생성기와 DB가 자원을 공유했고 CPU·GC 등은 수집하지 않았다. 폐쇄형 부하이므로 초당 요청은 최대 처리량이 아니다. 모두 만료된 이력에 대한 읽기만 측정하여 활성 선점·예약 및 인덱스 유지에 따른 쓰기 비용은 검증하지 않았다. `INVISIBLE`은 인덱스를 없앤 상태와 물리적으로 같지 않다.

원본 요약은 `result-abab-1-before-vu50.json`부터 `result-abab-4-after-vu50.json`까지다. 실험 서버는 종료했으며 실험 DB는 보존했다.

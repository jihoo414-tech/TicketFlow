# 점유 이력 조회 개선 전후 비교

## 변경과 측정 조건

좌석 조회의 점유 조건을 Java 필터에서 DB 쿼리로 옮겼다. `RESERVED` 또는 만료 전 `HELD`만 반환한다. 상세 결정은 ADR 0013에 기록했다.

2026-10-30 Windows 로컬 환경에서 MySQL 8.4.11, k6 2.2.0과 Spring Boot를 같은 PC에서 실행했다. 6,000석, 만료된 `HELD` 이력, 5초 예열 후 30초 측정, VU별 응답 후 1초 대기, SQL 로그 비활성화 조건이다. 각 수치는 1회 측정 결과이며 HTTP 200만 검사한다.

1,000건과 6,000건 개선 후 측정은 동일한 스키마와 생성 스크립트로 만든 별도 DB를 사용했다. 6,000건에서는 이력 생성 배치 구성이 개선 전과 다르다. 12,000건은 개선 전과 동일한 DB를 사용했다. 서버는 측정 사이 재시작됐으며 PC의 다른 부하나 캐시 상태는 통제하지 못했다.

## 이력 증가: 5 VU

| 이력 | p95 개선 전 | p95 개선 후 | HTTP 실패율 전/후 |
|---:|---:|---:|---:|
| 1,000 | 146.52ms | 118.09ms | 0% / 0% |
| 6,000 | 316.60ms | 109.62ms | 0% / 0% |
| 12,000 | 538.29ms | 138.35ms | 0% / 0% |

## 사용자 증가: 이력 12,000건

| VU | p95 개선 전 | p95 개선 후 | 초당 요청 전 | 초당 요청 후 | HTTP 실패율 전/후 |
|---:|---:|---:|---:|---:|---:|
| 5 | 538.29ms | 138.35ms | 3.48 | 4.52 | 0% / 0% |
| 20 | 1.90초 | 245.21ms | 8.07 | 17.40 | 0% / 0% |
| 50 | 4.93초 | 375.21ms | 9.06 | 40.16 | 0% / 0% |

50 VU에서 p95가 약 92% 낮아졌다. 측정 조건에서 결과는 DB에서 불필요한 이력을 걸러 반환 데이터를 줄인 것이 지연 감소에 기여한다는 가설과 일치한다. 단, 단발 측정이고 자원·DB 실행 계획을 수집하지 않아 정확한 비용의 원인과 분포는 확정할 수 없다.

모든 이력이 만료된 단순 시나리오라 개선 후 점유 이력 반환 건수가 0이다. 활성 선점과 예약이 섞인 실제 데이터에서는 결과가 다를 수 있다. 테스트는 상태 코드만 확인하며, 자동화 테스트에서는 선점 만료 경계와 예약 좌석 상태 등을 확인한다. VU별 대기가 있는 폐쇄형 부하이므로 초당 요청 수는 최대 처리량이나 실제 12만 명의 수용 능력이 아니다.

원본 k6 요약은 `result-matrix-*-vu*.json`(개선 전)과 `result-after-*-vu*.json`(개선 후)이다. 실험 서버는 종료했으며 테스트 DB는 보존했다.
